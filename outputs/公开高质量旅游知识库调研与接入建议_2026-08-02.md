# 公开高质量旅游知识库调研与接入建议

> 调研对象：`TravelPlanAssistant`  
> 调研日期：2026-08-02  
> 核验范围：官方旅游开放平台、全球开放知识基础设施、GitHub 项目、学术与科研数据集  
> 说明：许可证判断基于调研时公开页面，不构成法律意见；正式商用前应再次核验最新条款及每条记录的来源许可。

---

## 1. 核心结论

公开的高质量旅游数据和知识库**确实存在**，其中不乏国家旅游机构、Wikimedia、开放地图基金会及大型研究机构维护的数据。然而，没有单一来源能够同时满足以下全部需求：

- 全球和中国地区广覆盖；
- 高质量中文旅行攻略；
- 景点、餐饮、住宿、交通的结构化 POI；
- 实体关系、多语言名称和稳定 ID；
- 实时票价、库存、营业状态和交通时刻；
- 许可清晰且便于商业落库。

因此，`TravelPlanAssistant` 不应寻找一个“万能旅游知识库”，而应采用分层、多源、可追溯的组合架构：

```text
旅行叙事与 RAG        Wikivoyage
        │
实体主键与关系图谱      Wikidata
        │
全球基础 POI           Overture Places / FSQ OS Places
        │
地图、设施与交通细节    OpenStreetMap
        │
旅游 POI 快速 API       OpenTripMap
        │
重点目的地官方增强      DATAtourisme / 德国旅游知识图谱 / 城市官方 API
        │
动态事实                地图、天气、交通、票务、酒店库存等实时 API
```

### 最推荐的近期 PoC

1. **Wikivoyage**：补充目的地叙事、玩法、交通、餐饮和住宿建议，进入 RAG。
2. **Wikidata**：用 QID 统一城市、景点、行政区和世界遗产实体。
3. **OpenTripMap**：快速验证附近景点、分类检索和 POI 详情接口。
4. PoC 成功后，再引入 **Overture Places** 批量落库，并以 `confidence` 和多源匹配做质量过滤。

## 3. 高价值全球基础数据源详解

## 3.1 Wikivoyage：最适合旅行叙事 RAG

- **建设主体**：Wikimedia Foundation 旗下协作式旅行指南。
- **内容形态**：目的地介绍、抵达方式、当地交通、景点、餐饮、住宿、购物、安全和旅行主题。
- **格式/接入**：MediaWiki Action API、Core REST API、Wikimedia dumps；正文是 wikitext/HTML，可清洗后切块。
- **多语言**：有中文站；不同语言版本不是简单翻译，覆盖深度会不同。
- **许可**：CC BY-SA。应保留文章 URL、标题、版本/修订号、作者贡献页或合适署名，并评估衍生内容的相同方式共享义务。
- **优点**：比普通 POI 库更懂“为什么去、怎么玩、住哪里、注意什么”。
- **局限**：价格、营业时间和交通时刻可能过时；内容结构虽有惯例，但不是严格数据库 schema。

**适合接入位置**：`backend/data` 的目的地指南正文、RAG parent chunks 和引用溯源层。

## 3.2 Wikidata：最适合实体统一和关系查询

- **规模**：官方数据访问页在调研时显示超过 1.2 亿个 Item。
- **数据能力**：实体类型、坐标、多语言名称、别名、行政区、国家、创建时间、官方网站、世界遗产关系等。
- **访问方式**：
  - Wikibase REST API；
  - MediaWiki Action API；
  - Linked Data JSON/RDF/TTL/NT/JSON-LD；
  - SPARQL Query Service；
  - Recent Changes SSE 变更流；
  - 全量 dumps；
  - Vector Database 和只读 MCP。
- **许可**：CC0，无强制署名要求，但官方建议注明 Wikidata 来源。
- **优点**：QID 非常适合充当多源数据的统一实体键。
- **局限**：属性完整度不一致；公共 SPARQL 不适合大规模全库拉取。

**建议字段**：`wikidata_qid`、`labels`、`aliases`、`instance_of`、`located_in`、`coordinate`、`official_website`、`heritage_status`。

## 3.3 Overture Maps Places：最适合大规模商业 POI 基础库

- **规模**：2026 年 7 月文档约 7,500 万 Place；来源包括 Meta、Microsoft、Foursquare、PinMeTo 等。
- **主要字段**：`id`（GERS ID）、名称、地址、网站、电话、分类层级、`basic_category`、经纬度、`confidence`。
- **分类体系**：约 2,300 个层级类别，约 280 个 basic categories，适合搜索、图标和 LLM 粗分类。
- **更新**：每月发布；提供 GERS registry、bridge files 和 changelog。
- **获取**：Amazon S3、Azure Blob、STAC、Parquet，可用 DuckDB 或 Python Client 按边界框抽取。
- **许可**：按来源为 CDLA-Permissive-2.0 或 Apache-2.0；当前 Places 文档明确不含 OSM 数据，因此本身不承担 ODbL share-alike。
- **已知质量问题**：官方明确承认仍有重复、垃圾记录和属性缺失；`confidence` 只衡量实体是否存在，不保证属性正确，也不能解决重复。
- **版本注意**：分类 schema 正在演进，旧 `categories` 计划被 `taxonomy` 与 `basic_category` 取代，接入层不能把第三方字段名硬编码到业务域模型。

**建议**：生产前先抽取 3—5 个中国城市做准确率、重复率、名称中文率和属性完整度抽样。

## 3.4 FSQ OS Places：许可友好的 POI 补充源

- **建设主体**：Foursquare。
- **用途**：全球地点、类别和基础属性数据。
- **许可**：Apache-2.0；分发时需要保留相应的版权与 `NOTICE.txt`/attribution 要求。
- **注意**：FSQ OS Places 的公开规模、覆盖国家及访问门槛会随发布版本变化。调研时官网首页展示的当前口径与早期宣传口径存在差异，因此集成时应以实际下载版本的数据卡和 NOTICE 为准，不能把历史宣传数字写死到系统中。

**建议**：把它作为 Overture 的交叉验证和属性补齐候选，而不是在第一阶段同时维护两套超大 POI 主库。

## 3.5 OpenStreetMap：地图、交通和设施细节最强

- **数据**：道路、步行网络、公共交通节点、景点、餐饮、住宿、停车场、无障碍等大量标签。
- **获取**：官方 Planet XML/PBF、历史 dumps、地区切片、Overpass 等。
- **更新**：Planet 周期快照，也可消费分钟/小时/日级差分。
- **许可**：ODbL 1.0；必须署名。在与其他数据融合时，需要判断是否形成衍生数据库或集合数据库。
- **局限**：不同地区由社区维护，标签完整度和准确度差异显著；公共 Overpass 不应承担生产级大批量请求。

**建议**：以独立 OSM 数据层保存，保留 OSM ID、原始标签和 attribution，避免与宽松许可数据无边界混表。

## 3.6 OpenTripMap：旅游 POI PoC 速度最快

- **规模**：官方 API 页面称覆盖超过 1,000 万个全球旅游景点和设施。
- **来源**：融合 OSM、Wikidata、Wikipedia 等开放源。
- **API**：附近地点、地点详情、自动补全、地名转坐标；JSON/GeoJSON。
- **语言**：可指定语言；缺失时回退到英文或其他可用语言。
- **许可**：ODbL；官方明确允许预取、索引、存储、缓存和修改，但仍需遵守 ODbL 和署名要求。
- **局限**：聚合源带来的字段时效和重复问题仍需自检；API 配额、服务稳定性和全量离线能力要按套餐核验。

**建议**：作为第一阶段 API 数据源很合适，长期是否成为主库要根据调用成本和合规设计决定。

## 4. 官方旅游知识库与开放 API

## 4.1 法国 DATAtourisme

- 法国国家级旅游供给数据平台，现由 ADN Tourisme 与地方旅游机构共同维护。
- 覆盖景点、住宿、餐饮、活动、路线和其他旅游对象。
- 有国家旅游本体，适合语义互操作和结构化查询。
- 支持 RDF/N-Triples、CSV、API/定制 feed 等方式；机构源数据持续更新。
- 采用法国 `Licence Ouverte 2.0` 的开放数据体系，通常允许商业复用，但要求注明来源和更新时间。
- 属于本次调查中成熟度最高的“官方旅游知识库”案例之一。

## 4.2 German Tourism Knowledge Graph

- 由德国国家旅游局与 16 个州级旅游组织共同建设。
- 覆盖景点、路线、活动、餐厅、住宿与旅游基础设施。
- 使用 schema.org 扩展、RDF、SPARQL、RML 和 SHACL，强调标准化与数据校验。
- 2023 年起提供公共访问方向，API 通常需申请 key。
- 不应假定整个图谱只有一个统一许可；应保存每条记录或数据提供方的具体许可信息。
- 最值得借鉴的是其“旅游领域 schema + 多机构供数 + SHACL 校验 + 可追溯许可”的治理方式。

## 4.3 瑞典、首尔与斯德哥尔摩

- **Visit Sweden National API**：全国多地区结构化旅游数据，采用 schema.org 思路；适合作国家级内容增强。
- **Visit Seoul API**：官方景点、餐饮、住宿、购物和活动，多语言数据对中文用户友好。
- **Stockholm Open API**：城市级地点和活动，人工编辑质量较高，但覆盖范围有限。

这些 API 的共同特点是**内容权威、范围明确、时效通常优于社区静态库**；共同局限是**只覆盖单一国家或城市，且调用额度、贡献者权利和记录级许可需要逐项核验**。

## 4.4 中文官方开放数据

中文旅游开放数据目前较分散：

- 中国台湾台北旅游网和 TDX 提供相对完整的景点、餐饮、住宿、活动和 GIS API；
- 中国大陆一些地方政府开放平台提供景区名称、等级、介绍、门票、开放时间、经纬度、承载量、交通路线等字段；
- 不同城市平台的接口稳定性、更新频率、申请流程和许可证差异较大，暂时不适合直接当作全国统一主库。

**建议**：以“目的地插件”方式接入地方官方源，每个适配器独立维护 schema、授权、更新策略和健康检查。

## 5. GitHub 与学术数据集判断

## 5.1 TravelPlanner：强烈建议引入评测，不建议当事实库

- ICML 2024 Spotlight 旅行规划 Agent 基准。
- 任务要求同时规划交通、每日餐食、景点和住宿，并满足环境、常识和硬约束。
- 仓库包含 `database`、`evaluation`、`finetuning_data`、工具和 Agent 实现。
- GitHub 仓库许可证为 MIT；2026-05-24 仍有提交。
- 适合迁移到本项目的资产：
  1. 行程 JSON schema；
  2. 预算、房型、餐食、交通和空间可行性约束；
  3. 离线验证集与 pass-rate 思路；
  4. tool-use 与 sole-planning 双模式评测。
- 不应直接用其中的数据库回答实时旅行事实问题。

## 5.2 IntTravel：推荐系统研究价值极高，生产知识库价值有限

- 由高德/Alibaba Group 研究团队发布。
- 约 1.628 亿用户、41.298 亿交互、729 万 POI。
- 交互包含时间、行为类型、POI、地理块、行政区、天气、出行方式、途经 POI 等。
- 适合研究“何时出发、去哪里、如何出行、途中需求”等多任务推荐。
- POI 使用匿名 ID 和离散特征，不是可直接展示的景点内容库。
- GitHub README 未展示明确开源许可证；正式商用、模型训练或二次分发前必须向发布方确认。

## 5.3 中国旅游科研数据

### 甘肃旅游知识图谱

- 约 30,045 个实体、14 种关系、810,793 个三元组，含景点、酒店和美食。

## 6. 面向 TravelPlanAssistant 的推荐数据架构

## 6.1 领域主模型

建议建立与数据源无关的内部实体模型，至少包含：

```json
{
  "entity_id": "internal:poi:...",
  "entity_type": "attraction|restaurant|lodging|transport|event|destination",
  "canonical_name": "故宫博物院",
  "names": {"zh-CN": [], "en": []},
  "location": {
    "country": "CN",
    "admin1": "北京市",
    "locality": "北京市",
    "latitude": 39.9163,
    "longitude": 116.3972
  },
  "categories": [],
  "external_ids": {
    "wikidata": "Q...",
    "overture_gers": "...",
    "osm": "node/...",
    "opentripmap": "..."
  },
  "facts": [],
  "descriptions": [],
  "source_records": [],
  "freshness": {
    "retrieved_at": "ISO-8601",
    "source_updated_at": "ISO-8601",
    "expires_at": "ISO-8601|null"
  }
}
```

每个 `source_record` 必须保存：

```json
{
  "source": "wikidata",
  "source_id": "Q...",
  "source_url": "https://...",
  "license": "CC0-1.0",
  "attribution": "Source: Wikidata",
  "retrieved_at": "ISO-8601",
  "raw_hash": "sha256:..."
}
```

## 6.2 数据分层

1. **Raw 层**：原样保存 API/dump 记录及许可证元数据，不直接给用户。
2. **Normalized 层**：统一字段、坐标、语言和类别，不丢 `source_id`。
3. **Entity Resolution 层**：利用 Wikidata QID、GERS ID、OSM ID、名称/地址/坐标匹配合并实体。
4. **Knowledge 层**：事实与描述分开；事实保留时间有效性，描述进入 RAG。
5. **Serving 层**：
   - 结构化过滤/附近检索；
   - RAG 文本检索；
   - 实时工具调用；
   - 引用和许可证展示。

## 6.3 不应静态化的事实

以下字段不要只依赖静态知识库，应在生成行程时实时查询：

- 酒店和机票价格、库存；
- 列车/航班时刻与延误；
- 景点临时闭园、预约余量；
- 当日营业状态；
- 天气、灾害和交通管制；
- 汇率和门票促销。

静态库可以保存“通常开放时间”“价格区间”和“查询入口”，但最终回答应注明实时查询时间。

## 7. 分阶段实施路线

## 阶段 0：合规和 schema 基础

- 建立 `source_registry`，记录来源、许可证、署名模板、是否允许缓存、是否允许衍生数据库和更新频率。
- 给每条知识保留来源，不允许“清洗后丢来源”。
- 将 ODbL 数据与宽松许可数据分层保存，融合前评估数据库许可影响。
- 建立内部统一实体 schema，不让业务代码直接依赖第三方字段。

## 阶段 1：低成本 PoC

**Wikivoyage + Wikidata + OpenTripMap**

- 选北京、成都、三亚、大理四个已有目的地。
- Wikivoyage：抓取目的地正文并按章节切块，附版本和署名。
- Wikidata：补 QID、多语言名、坐标、类型和行政区。
- OpenTripMap：补附近景点、类别和详情。
- 测试指标：实体召回率、重复率、中文描述覆盖率、过期事实比例、回答引用正确率。

## 阶段 2：全球 POI 批量底座

**Overture Places + 可选 FSQ OS Places**

- 先按城市边界框抽取 Parquet，不下载全球全量。
- 使用 `confidence` 阈值，但额外执行同名近距离去重和中文名称覆盖检查。
- 保存 GERS ID 和 release version，通过 changelog 做增量同步。
- 与 Wikidata/OSM 的合并关系单独记录，不覆盖原始记录。

## 阶段 3：地图与设施增强

**OpenStreetMap**

- 补步行网络、公共交通节点、停车、厕所、无障碍、入口等信息。
- 生产环境使用地区 PBF/自建索引或合规服务，不滥用公共 Overpass。
- 单独管理 ODbL 署名和数据库边界。

## 阶段 4：重点国家与城市官方增强

- 法国：DATAtourisme。
- 德国：German Tourism Knowledge Graph。
- 瑞典：Visit Sweden / Stockholm API。
- 韩国首尔：Visit Seoul API。
- 中国台湾台北：台北旅游网 / TDX。
- 中国大陆：按目的地逐个接地方政府开放平台，不一次性承诺全国覆盖。

## 阶段 5：规划质量评测

- 借鉴 TravelPlanner 构造本项目评测集。
- 指标不只看语言流畅度，还应检查：预算、时间冲突、距离、餐食完整性、住宿连续性、开放时间、用户硬约束和实时信息引用。
- IntTravel 只在许可证获得确认且确实需要推荐建模时再评估，不作为当前 RAG 建设的前置依赖。

## 8. 最终优先级建议

### 立即做

1. 用 Wikidata QID 给现有目的地和景点建立统一 ID。
2. 对 4 个已有目的地做 Wikivoyage 小规模增量导入实验。
3. 接 OpenTripMap 做附近 POI API 适配器。
4. 在所有知识记录中加入 `source`、`source_id`、`license`、`attribution`、`retrieved_at`。
5. 建立静态事实与实时事实边界。

### PoC 验证后做

1. Overture Places 城市级 Parquet 抽取与去重评估。
2. 引入 TravelPlanner 风格的约束评测。
3. 为目标目的地增加官方 API 适配器。
4. 设计数据变更、过期和冲突解决策略。

### 暂时不要做

1. 不要直接合并携程等商业平台爬虫 CSV。
2. 不要把非商业科研数据混入未来可能商用的生产库。
3. 不要一开始就下载和维护全球 OSM、Wikidata、Overture 全量数据。
4. 不要把静态知识库当作实时价格和营业状态来源。
5. 不要仅凭 GitHub 仓库有 MIT/Apache 许可证，就认定仓库内第三方数据也获得同等授权。

## 10. 一句话决策

如果目标是尽快把 `TravelPlanAssistant` 的知识质量拉高，优先选择 **Wikivoyage（叙事）+ Wikidata（实体）+ OpenTripMap（旅游 POI API）**；如果目标转向规模化全球生产，再增加 **Overture Places（POI 主库）+ OpenStreetMap（地图和设施）+ 重点目的地官方 API（权威增强）**，同时将所有来源、许可和更新时间纳入数据模型。
