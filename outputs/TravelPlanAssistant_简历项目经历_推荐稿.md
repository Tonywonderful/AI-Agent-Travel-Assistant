# TravelPlanAssistant 简历项目经历推荐稿

## 一、推荐直接放入简历的版本

**2026.XX-2026.XX　AI 智能旅行规划与问答助手**

- **项目描述：** 面向中文旅行场景，构建融合 RAG、LLM Tool Calling 与高德地图能力的智能旅行规划系统；根据目的地、日期、预算、人数及偏好生成结构化行程，并提供天气/路线补全、AI 对话问答及历史行程管理。
- **核心技术：** FastAPI、LangChain、ChromaDB、Redis、SQLite、SQLAlchemy、FastMCP、Vue 3、TypeScript、高德地图 API

1. **RAG 检索与评估：** 面向口语化、复合型旅行需求，构建 Query Rewrite + Chroma 向量召回 + Cross-encoder Rerank 两阶段检索链路；按 `destination` 元数据在召回阶段隔离城市，并在模型/向量库不可用时降级至规则改写与关键词检索。围绕 6 城 676 个语义 Chunk 建立 18 条固定查询及 528 条 0-3 级 qrels，当前固定口径评测达到 Recall@20 60.6%、Precision@5 74.4%、nDCG@5 69.9%。
2. **生成可信性治理：** 针对大模型可能编造景点、餐厅名称的问题，设计代码级名称回查机制，对模型结果进行归一化、候选集精确匹配和攻略正文子串校验；无法从本次检索上下文归因的实体自动丢弃，并回退至真实候选或留空，将“只使用真实名称”由 Prompt 软约束落实为程序硬校验。
3. **Agent 与流式交互：** 针对旅行问答意图不确定的问题，基于模型原生 Tool Calling 实现最多 3 轮自主调用，统一接入天气、地理编码、POI、路线、攻略检索和联网搜索 6 类工具；通过 SSE 输出 `status/tool_start/tool_result/token/error/done` 事件，并设计安全前缀缓冲，识别跨 Chunk 的 `<tool_call>` 标记泄漏，保障逐 Token 流式体验与响应完整性。
4. **知识库与缓存工程：** 基于 Markdown 二/三级标题进行语义分块，将餐厅、酒店等实体构造成独立 Chunk，并写入 category、entity_name、budget_tier 等元数据；通过 SHA-256 内容指纹 + SQLite 文档清单识别新增、修改、删除，实现 Chroma 文档级增量同步及 RAG/Rerank 缓存联动失效。使用 Redis 缓存天气、地图、检索与重排结果，Redis 异常时自动回退直连，避免缓存故障阻断主链路。

## 二、一页简历空间不足时的精简版

**2026.XX-2026.XX　AI 智能旅行规划与问答助手**

- **项目描述：** 构建融合 RAG、LLM Tool Calling 与高德地图的智能旅行规划系统，根据用户预算、日期及偏好生成结构化行程，并提供天气路线补全、流式问答和历史管理。
- **核心技术：** FastAPI、LangChain、ChromaDB、Redis、SQLite、Vue 3、TypeScript、高德地图 API

1. 构建 Query Rewrite + 向量召回 + Cross-encoder Rerank 两阶段检索，通过目的地元数据过滤消除跨城污染；基于 18 条固定查询、528 条分级 qrels 评测，Recall@20 / Precision@5 / nDCG@5 分别达到 60.6% / 74.4% / 69.9%。
2. 设计 LLM 实体名称回查机制，对景点和餐厅执行归一化及检索上下文校验，无法归因的名称自动丢弃并回退真实候选，将 Prompt 防幻觉约束升级为代码级硬校验。
3. 实现最多 3 轮 Tool Calling 与 6 类旅行工具统一调度，基于 SSE 逐 Token 输出；通过安全前缀缓冲解决跨 Chunk 工具标记泄漏，并在工具或模型异常时提供可解释降级。
4. 使用内容哈希 + SQLite 清单实现知识库增量同步，联动失效 Chroma 检索缓存；通过 Redis 缓存天气、地图、RAG 和 Rerank 结果，缓存故障时不阻断主链路。

## 三、如果投“AI 应用开发岗”，建议项目标题

优先级从高到低：

1. **AI 智能旅行规划与问答助手**（最稳，产品与技术都清楚）
2. **基于 RAG 与 Tool Calling 的智能旅行规划系统**（技术导向更强）
3. **多工具协同的 AI 旅行规划平台**（适合强调 Agent，但弱化 RAG 指标）

不建议写“LangGraph 旅行 Agent”：当前行程生成主链路是固定服务编排，对话助手才是模型自主 Tool Calling；硬写 LangGraph/全流程 Agent 容易被面试官追问穿。

## 四、数字与措辞的使用边界

### 可以写

- 6 个目的地城市。
- 当前知识库按源码实际切出 676 个非空 Chunk，其中 149 个餐厅实体 Chunk、211 个酒店实体 Chunk。
- 18 条固定评测 Query、528 条 qrels 标注项。
- 最新固定 20 槽位口径：Recall@20 60.6%、Precision@5 74.4%、nDCG@5 69.9%。
- 对话最多 3 轮 Tool Calling、6 类工具、6 种 SSE 事件。
- 已建立 25 个后端测试文件；本次核验结果为 132 passed、6 failed，失败主要来自知识库实体格式升级后的旧测试/旧评估字段漂移。

### 暂时不要写

- “Top-1 从 X% 提升到 Y%”“MRR 提升到 X%”：当前固定评估入口已统一为 Recall@20、Precision@5、nDCG@5，没有同口径的优化前后对照。
- “缓存使延迟下降 X% / API 成本下降 X%”：代码具备缓存，但尚无命中率、P95 延迟和成本 A/B 数据。
- “系统支持高并发 / QPS 达到 X”：未做正式压测。
- “测试全部通过”：当前是 132 passed、6 failed，不能写全绿。
- “实时自动同步知识库”：当前由 CLI 轮询脚本触发，不是后台常驻服务。
- “全流程 Agent / LangGraph 工作流”：源码中没有 LangGraph；固定行程生成采用显式编排。

## 五、进一步增强简历含金量的补测顺序

1. 固定同一份语料、Query 与 qrels，保存“纯向量检索”和“Query Rewrite + Rerank”两组结果，形成可写的前后对比。
2. 开启 Redis，分别执行冷请求与热请求，记录 RAG、天气、地图接口的 P50/P95、命中率及外部 API 调用次数。
3. 修复 6 个漂移测试，保证完整测试套件全绿后再写“138 项测试全部通过”。
4. 对 30-50 份生成行程自动统计“无法从检索上下文归因的实体比例”，将名称回查亮点量化为幻觉拦截率。
5. 对行程生成链路做 5/10 并发压测；当前外部调用多数同步串行，先异步化再写吞吐提升数据。

## 六、面试时的 30 秒介绍

这是一个完整的 AI 旅行规划产品，不是只调用一次大模型的 Demo。系统先把用户的目的地、预算和偏好改写为检索 Query，再通过 Chroma 向量召回和 Cross-encoder 重排获得攻略上下文，最后生成结构化行程。为了控制幻觉，我没有只依赖 Prompt，而是在服务层对模型产出的景点和餐厅名称做代码级回查；无法从检索上下文归因的名称会被丢弃并回退真实候选。对话侧则采用 Tool Calling，让模型自主调用天气、POI、路线、攻略和联网搜索，并通过 SSE 逐 Token 返回。项目还实现了 Redis 可降级缓存、内容哈希驱动的知识库增量同步，以及固定 Query + 分级 qrels 的 RAG 评估体系。
