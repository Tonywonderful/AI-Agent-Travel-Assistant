# 成都用户端真实多路检索与行程异常根因报告

## 1. 诊断结论摘要

本次不是调用单路 Retriever，也没有使用 `tests/`、`scripts/test_*.py` 或测试脚本中的请求数据，而是通过真实用户端生产入口执行：

```text
POST http://127.0.0.1:8011/trip/generate
```

诊断进程没有修改业务源码或业务算法，只在当前请求内强制 RAG/Rerank 缓存未命中，以确保 Query Embedding、向量召回和 Cross-encoder 重排都实际执行。最终接口返回 HTTP 200。

生产链路确认包含 3 路检索：

1. 主综合路：向量 Top10 → Cross-encoder Top5。
2. 住宿补充路：向量 Top6 → Cross-encoder Top2。
3. 餐饮补充路：向量 Top6 → Cross-encoder Top2。

三路均真实执行 Ollama `qwen3-embedding:4b` Query Embedding，三路重排模式均为 `cross_encoder`，没有使用规则重排 fallback。

第二张截图中的问题不是一个模型单点故障，而是多个阶段共同造成：

- 前端只传预算上限，而且“人均预算”与后端“总预算”语义不一致。
- 住宿、餐饮补充 Query 没有携带用户的档次、饮食偏好和预算。
- 已入库的 `category`、`budget_tier` metadata 没有用于向量召回硬过滤。
- Planner schema 缺少酒店、活动和结构化交通字段。
- 名称校验只覆盖景点和餐厅，且对子串放行过宽。
- 最终组装层把酒店、餐次、时间和交通写成固定模板。
- 地图层拿模糊的“成都 出发点”做驾车路线，放大成 35–51 km 的错误距离。
- 预算层按名称关键词估票价，没有读取 RAG 中明确的“免费”。

## 4. Query Rewrite 阶段

### 4.1 输入

Query Rewrite 收到了：目的地、旅行偏好、节奏、备注；没有收到 `dietary_preferences`、`hotel_level` 和预算。

### 4.2 Nemotron 输出

```text
成都 自然风景 城市漫游 美食探索 轻松 当地文化 温泉体验
地铁出行 减少换乘 宽窄巷子 锦里 人民公园 青城山
都江堰 火锅 串串 茶馆文化
```

Token：

- Prompt：204
- Completion：409
- 来源：LLM Rewrite

### 4.3 判断

优点：备注里的“温泉、地铁、减少换乘”被保留下来，也补充了成都代表性实体。

问题：这条 Query 同时混合景点、餐饮、温泉、交通方式和路线组织等多种意图。Cross-encoder 面对单个景点 Chunk 时，很难认为它完整回答了这条宽 Query，所以主路 Top5 分数全部极低（最高仅 0.0122）。

更关键的是，饮食偏好“本地特色、海鲜”、酒店档次“舒适型”和预算没有进入 Rewrite。它们也没有进入两个补充 Query，因此后续无法可靠落实。

## 9. Nemotron PlannerDraft

模型：`nemotron-3-ultra-free`，结构化草稿生成成功。

Token：

- Prompt：2135
- Completion：2541

逐日结果：

| Day | 景点 | 餐厅 | 关键备注 |
|---:|---|---|---|
| 1 | 人民公园 | 芙蓉凰 | 入住如家商旅；写地铁 1 号线 |
| 2 | 宽窄巷子 | 柴门荟 | 从人民公园步行约 10 分钟 |
| 3 | 桂溪生态公园 | 芙蓉凰 | 写地铁 1 号线 |
| 4 | 成都自然博物馆 | 柴门荟 | 写地铁 3 号线 |
| 5 | 锦里古街 | 芙蓉凰 | 写打车去青城山周边温泉酒店 |

### 9.1 Planner 做对的部分

- 景点和餐厅都来自传入上下文。
- 生成了 5 天完整结构化草稿。
- 在自然语言摘要、tips 和 daily_note 中尝试响应“轻松、地铁、减少换乘、温泉”。

### 9.2 Planner 的问题及其结构性原因

1. `PlannerDayDraft` 只有景点、餐厅和 `daily_note`，没有酒店、交通或活动字段。
2. Planner 摘要中写“住宿选用如家商旅成都门店”，但服务层无法读取一个结构化酒店字段。
3. 温泉只能写进 `daily_note`/`tips`，无法做实体归因、POI 补全和预算计算。
4. “青城山周边温泉酒店”不在 9 条上下文中，属于未校验的模型补充。
5. 5 天只有 2 家餐厅，模型只能重复。

另有一个提示词候选提取缺陷：`trip_planner_agent.py:177-180` 用中文方括号 `【...】` 提取酒店和餐厅名，但真实上下文标题格式是：

```text
[来源: chengdu_guide.md | 标题: 成都W酒店]
```

因此“可选真实酒店/餐厅”列表很可能显示为“暂无”，即使上下文正文里已有实体。

## 10. fallback_candidates 与名称校验

正式候选池：

```json
{
  "spots": [
    "人民公园（城市生活）",
    "宽窄巷子景区",
    "锦里古街（历史街区与夜游）",
    "桂溪生态公园（城市公园）",
    "成都自然博物馆（成都理工大学博物馆）（自然科学与亲子）"
  ],
  "meals": ["芙蓉凰", "柴门荟"],
  "hotels": ["成都W酒店"]
}
```

如家条目是品牌门店集合提示，不是一个具体酒店实体，因此不会进入正式酒店池。这一点本身正确。

但名称校验存在覆盖缺口：

- 只校验 `spot_name` 和 `meal_name`。
- 不校验 Planner 摘要、tips、daily_note、酒店名、温泉活动和交通描述。
- `name_guard.py:114` 允许名称只要出现在全部上下文拼接字符串中就放行，不要求命中对应 category，存在跨类别误放行风险。

因此“青城山周边温泉酒店”绕过了校验，最终作为备注和 tips 保留下来。

## 11. Planner 草稿与最终 Itinerary 的字段级变化

| 字段 | Planner | 最终结果 | 变化来源 |
|---|---|---|---|
| 酒店 | 摘要/备注写如家商旅 | 每天成都W酒店 | `fallback_hotel_names[0]` 固定取第一个正式酒店 |
| 酒店档次 | 用户要求舒适型 | 成都W酒店被标成舒适型 | 名称来自 RAG，level 直接复制请求值 |
| 交通 | 多处写地铁/步行 | 每天结构化交通均为打车 | `TransportItem(mode="打车")` 硬编码 |
| 起点 | 酒店/上一地点语义 | 成都 出发点 | `from_place=f"{destination} 出发点"` 硬编码 |
| 餐次 | 多天说明为晚餐 | 全部 `meal_type=午餐` | 组装层硬编码 |
| 时间 | “上午10点后”“傍晚夜游” | 每天 10:00–12:00 | 景点时间硬编码 |
| 温泉 | Day5 备注 | 仍只是备注，没有结构化活动 | schema 无活动字段，未地图补全/校验 |
| 门票 | RAG 多处明确免费 | 人民公园 30、宽窄巷子 40、锦里 35 | 名称关键词散列估价 |

最明显的自相矛盾是：

```json
{
  "name": "成都W酒店",
  "level": "舒适型"
}
```

餐次也出现同类矛盾：

```json
{
  "meal_type": "午餐",
  "notes": "适合晚餐细细品味精致川味。"
}
```

## 12. 地图补全与异常距离

服务层先构造：

```py
TransportItem(
    mode="打车",
    from_place="成都 出发点",
    to_place=spot_name,
)
```

地图层随后对起终点做 POI/地理编码，并固定调用 `/direction/driving` 驾车路线。

最终距离：

| Day | 目的地 | 距离 | 时间 |
|---:|---|---:|---:|
| 1 | 人民公园 | 46.66 km | 48 分钟 |
| 2 | 宽窄巷子 | 47.05 km | 48 分钟 |
| 3 | 桂溪生态公园 | 51.00 km | 42 分钟 |
| 4 | 成都自然博物馆 | 35.47 km | 31 分钟 |
| 5 | 锦里古街 | 45.00 km | 53 分钟 |

“成都 出发点”不是一个真实 POI，地图服务只能猜测匹配，导致所有城区路线从错误起点计算。之后 `_apply_route_based_transport_costs` 又按这些错误公里数计算打车费，产生每日约 ¥88–¥122 的交通成本。

即便用户明确偏好地铁，地图层也只实现驾车路线，没有公共交通/地铁路线模式。

## 13. 预算结果与问题

最终预算：

| 类别 | 金额 |
|---|---:|
| 交通 | ¥545.39 |
| 酒店 | ¥2,653.50 |
| 餐饮 | ¥1,167.54 |
| 门票 | ¥213.00 |
| 其他 | ¥960.00 |
| 合计 | ¥5,539.43 |

该合计在数学上与当前条目相符，但业务语义并不可靠：

1. 输入的 ¥8,000 是界面人均上限还是后端总预算不明确。
2. 酒店费用不是从酒店知识库参考价格生成，而是从总预算按比例拆分。
3. 餐饮费用不是从餐厅“人均预算 × 2 人”生成，导致两家人均 500 元以上餐厅最终单日只估约 ¥223–¥258。
4. 免费景点被估出门票。
5. 交通费基于错误的 35–51 km 驾车路线。
6. `other=budget * 12%`，直接得到 ¥960，模板属性明显。

因此 ¥5,539.43 只能视为当前规则计算结果，不能视为该行程的可信预算。

## 14. 第二张截图问题逐项归因

## 15. 修复优先级建议

本报告只诊断，不在本轮修改业务代码。建议后续按以下顺序修复。

### P0：先修数据契约和硬矛盾

1. 明确预算语义：建议传 `budget_min_per_person`、`budget_max_per_person`，后端再按人数计算总预算；或前后端统一为总预算。
2. 酒店选择必须保留真实 metadata，禁止把用户请求档次覆盖到候选实体上。
3. 去掉固定 `打车`、`成都 出发点`、`午餐`、`10:00–12:00`。
4. 结构化交通起点应为当日酒店或上一活动地点。

### P1：让三路检索真正条件化

1. 主路只负责景点/活动，避免混入餐饮、住宿和交通方式。
2. 住宿 Query 加入：档次、预算、地铁偏好、区域；召回时硬过滤 `category=hotel` 和标准化 `budget_tier`。
3. 餐饮 Query 加入：`dietary_preferences`、人均预算；硬过滤 `category=restaurant`。
4. 餐饮候选数应根据天数动态扩展，并做实体去重/多样性约束。
5. 对用户必须满足但知识库无实体的要求，输出“暂无可核验候选”，不要让 Planner自由补全。

### P1：扩展 Planner 与校验 schema

建议单日草稿至少结构化包含：

- `activities[]`：名称、类型、时段、来源 chunk。
- `meals[]`：餐厅、餐次、预算、来源 chunk。
- `hotel`：具体实体、档次、参考价格、来源 chunk。
- `transport[]`：起点、终点、首选方式、备选方式。

名称校验应按 category/entity pool 校验，并覆盖 summary、tips、activity、hotel 和 transport 中的实体；不要只在全文 haystack 做跨类别子串放行。

### P2：地图与预算可信化

1. 根据 `transport.mode` 调用对应的步行/公交/驾车 API，而不是统一 driving。
2. POI 补全后，用酒店/上一地点的真实坐标计算路线。
3. 门票优先解析知识库字段中的“免费/具体价格/以官方为准”。
4. 餐饮按人均预算和人数估算，住宿按参考每晚价格和实际夜数估算。
5. 预算冲突时明确提示用户，而不是为了贴近输入预算强行按比例拆分。

### P2：可观测性

在生产请求级 Trace 中持续记录：

- 每路 Query、过滤条件、向量 TopK、Cross-encoder TopK。
- 每个最终实体对应的 source chunk id。
- Planner 字段到最终字段的覆盖/丢弃原因。
- 地图 POI 命中项与路线起终点坐标。

这样以后可以直接回答“某个酒店为什么被选中”，而不必再次插桩还原。

## 16. 最终结论

这次真实链路证明：系统不是没有执行多路检索或模型重排，而是“多路存在，但条件没有沿链路传到底”。

最关键的断点是：

```text
用户条件
  ├─ 酒店档次没有进入住宿 Query/过滤
  ├─ 饮食偏好没有进入餐饮 Query/过滤
  ├─ 地铁偏好没有进入结构化交通
  └─ 温泉没有可校验的活动实体
```

随后组装层又用固定模板覆盖 Planner 的自然语言意图，于是产生了第二张图中的连锁矛盾。优先修复“参数契约 → 条件化分路检索 → 结构化 Planner schema → 去硬编码组装”，会比单纯调整 Prompt 或更换模型有效得多。
