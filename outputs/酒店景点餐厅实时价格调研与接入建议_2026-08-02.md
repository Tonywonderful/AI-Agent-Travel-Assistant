# 酒店、景点与餐厅实时价格调研及接入建议

> 调研日期：2026-08-02  
> 适用项目：TravelPlanAssistant

## 一、结论

有办法查询价格，但没有一个面向普通开发者、稳定且合规的统一公开接口，可以同时返回任意酒店、任意景点和任意餐厅的完整实时成交价。

正确的工程方案是分别接入三类数据源，并由项目自己的统一价格服务归一化：

1. **酒店**：可以查询带入住条件的实时房价、房型、库存、税费和退改政策。
2. **景点门票**：可以查询票种和展示价；真正可售价格与库存通常需要游玩日期，并在下单前二次验价。
3. **餐厅**：公开 POI 接口通常只能提供人均消费或价格档位。任意餐厅的实时堂食菜单价、团购价并没有统一公开 API；完整菜单价格一般只对已授权商家或服务商开放。

因此，产品文案和数据字段必须区分：

- `实时可售报价`：带日期、人数和商品条件，且刚完成供应商验价。
- `报价快照`：搜索时有效，但预订前仍需二次确认。
- `人均参考价`：POI 平台统计值，不代表具体菜单或当天成交价。
- `估算价格`：由 TravelPlanAssistant 当前预算算法生成。

## 二、三类数据能做到什么

| 类别 | 可获得的数据 | 实时程度 | 主要限制 |
|---|---|---:|---|
| 酒店 | 酒店、房型、入住日期、价格、库存、税费、退改、预订链接 | 高 | 通常需要联盟或供应商资质；搜索价仍需预订前验价 |
| 景点门票 | 产品、票种、日期、场次、价格、库存、预订链接 | 中高 | 有些查询接口只返回展示价，日期库存需进一步确认 |
| 餐厅人均价 | 人均消费、价格档位、营业信息 | 中低 | 不是菜单价，也不是实时成交价 |
| 餐厅菜单价 | 菜品、SKU、库存、餐盒费、可售时间 | 高 | 通常仅限已授权门店，不可搜索任意平台商户 |
| 餐厅团购价 | 套餐、券价、有效期、购买链接 | 变化快 | 缺少稳定的通用公开 API，平台授权与条款限制明显 |

## 三、推荐数据源

### 1. 中国境内优先方案

#### 途牛 MCP

途牛官方 MCP 开放平台明确覆盖酒店和门票：

- 酒店：实时查询房型详情、价格、库存，并可继续完成预订。
- 门票：查询票种和价格，并可创建订单。
- 酒店生产 MCP 地址：`https://openapi.tuniu.cn/capabilities/mcp/hotel`
- 认证：OAuth 2.1；企业固定系统可申请 `client_id` 和 `client_secret`。

门票工具文档公开了：

- `query_cheapest_tickets`
- `create_ticket_order`

门票查询结果包含 `productId`、`resId`、`price` 和 `ticketType`。但当前公开查询参数主要是 `scenic_name`，游玩日期在下单阶段才出现。因此查询价应标记为“展示报价”，不能直接宣称为指定日期的最终库存价。

官方资料：

- https://platform-p.tuniu.com/mcp/
- https://platform-p.tuniu.com/mcp/docs/guide/mcp-auth.html
- https://platform-p.tuniu.com/mcp/docs/apidoc/mcp/ticketMCP.html

#### 飞猪 flyai Skill

飞猪官方开源的 `flyai` Skill/CLI 支持酒店与旅游商品搜索。酒店查询可传入目的地、地标、入住日期和退房日期，搜索结果可包含价格与预订链接。

酒店示例：

```bash
flyai search-hotel \
  --dest-name "Hangzhou" \
  --poi-name "West Lake" \
  --check-in-date 2026-04-10 \
  --check-out-date 2026-04-12
```

景点 POI 搜索与可售门票商品必须分开理解：`search-poi` 主要返回景点信息；门票商品更可能通过 `keyword-search` 或 `ai-search` 返回，接入前应实测 JSON 字段、日期条件和验价行为。

官方仓库：

- https://github.com/alibaba-flyai/flyai-skill

#### 高德地图

高德适合作为地点发现、实体消歧、地址与位置补全的数据源，不应被当作 OTA 报价源。

高德 POI 2.0 的业务信息可提供 `cost` 等人均消费字段，适合餐厅“人均参考价”；它不表示菜品实时价格，也不保证等于用户当次消费。

项目当前 `map_service.py` 使用高德 v3 `/place/text`，并设置 `extensions=all`，但归一化结果没有提取价格字段。后续可以升级或补充字段映射，将餐厅 `cost` 透传为 `average_cost_reference`，并明确标记为参考值。

### 2. 国际或出境游方案

#### 酒店

- **Booking.com Demand API**：面向 Affiliate Partners，支持住宿搜索、实时价格和可用性。
- **Expedia Rapid Lodging API**：支持实时房价、房型、费用、取消政策、可用性及价格二次校验。
- **Amadeus Hotel APIs**：适合开发和国际酒店搜索，生产环境可获取真实报价与可用性；测试环境不能代表全量生产数据。
- **TripO Hotel API**：主打酒店 availability 和 rates，可作为候选供应商，但应先验证覆盖率、合同、数据质量和售后能力。

#### 景点和活动

- **Viator Partner API**：支持产品内容、日期可用性、实时 availability check、价格计算、预订与取消。下单前必须调用 availability check 重新确认。
- **GetYourGuide API**：能够访问产品、选项和 availability，但合作门槛通常高于普通自助 API。
- **Amadeus Tours and Activities API**：可返回活动和供应商 deep link，适合补充产品发现，但 Self-Service 能力和覆盖范围需要按当前文档核验。

### 3. 不建议作为生产首选的方案

网络上存在声称可以抓取 Booking、Trip.com、美团、大众点评等实时数据的第三方代理 API。这些服务往往依赖代理池、验证码绕过或页面结构抓取，存在以下问题：

- 违反目标平台服务条款或数据授权边界的风险。
- 页面和反爬策略变化后接口容易失效。
- 价格语义、税费、币种、库存和退改字段可能不完整。
- 无法保证预订链路与售后责任。
- 可能泄露 Cookie、账号或用户查询信息。

它们最多适合隔离环境中的可行性验证，不应作为 TravelPlanAssistant 的默认正式数据源。

## 四、最适合 TravelPlanAssistant 的实施方案

### 阶段一：先建立统一价格语义

建议新建：

- `backend/app/services/price_service.py`
- `backend/app/services/price_providers/base.py`
- `backend/app/services/price_providers/tuniu.py` 或 `flyai.py`
- `backend/app/services/price_providers/amap_reference.py`
- `backend/app/tools/price_tools.py`

不要把交易报价逻辑继续堆进 `map_service.py`。地图服务负责“这个地点是谁、在哪里”，价格服务负责“在指定条件下卖多少钱”。

统一报价模型至少包含：

```python
class PriceOffer:
    entity_name: str
    entity_type: str
    provider: str
    product_id: str | None
    price: float
    currency: str
    price_type: str
    available: bool | None
    checked_at: datetime
    expires_at: datetime | None
    booking_url: str | None
    is_estimated: bool
    conditions: dict
    taxes_and_fees: float | None
    cancellation_policy: str | None
```

其中 `conditions` 应保存酒店入住日期、退房日期、人数和房型，或门票游玩日期、票种和场次。没有这些条件的数字不能标为完整实时价格。

### 阶段二：接酒店与门票真实报价

国内旅行场景优先评估途牛 MCP；如希望快速验证 Agent 商品搜索体验，可并行实测飞猪 `flyai`。

建议对外暴露四个独立工具：

```text
search_hotel_prices
search_attraction_tickets
get_restaurant_price_reference
confirm_offer_price
```

项目已有 `backend/app/mcp/server.py`，可沿用当前 FastMCP 注册模式对外暴露这些工具。

### 阶段三：餐厅先提供参考价

首版餐厅价格建议返回：

- 高德人均消费参考值。
- 价格采集来源和查询时间。
- “非菜单实时价”的显著标记。
- 餐厅官方菜单、团购或第三方预订链接（只有在合法获得时才返回）。

除非项目以后取得美团等平台的商家/服务商授权，否则不要承诺“任意餐厅实时菜单价”。美团门店菜品接口虽然能返回菜品价格、SKU、库存、售罄状态和餐盒费，但它需要业务授权和门店授权凭证，不能作为公开商户搜索接口使用。

### 阶段四：保留现有估算作为降级能力

当前 `backend/app/services/trip_service.py::_estimate_ticket_cost()` 根据关键词估算门票，酒店和餐饮预算也主要依赖预算权重拆分。建议保留这些算法作为 fallback：

```text
供应商报价成功 -> 使用真实报价快照，记录 provider 和 checked_at
供应商超时/无结果 -> 保留现有估算，标记 is_estimated=true
用户进入预订 -> 调用 confirm_offer_price 再次验价
```

不要静默地用估算值冒充实时价格。

## 五、缓存与验价建议

| 数据 | 建议缓存 | 使用规则 |
|---|---:|---|
| POI 基础信息 | 1—7 天 | 名称、地址、类型等可长期缓存 |
| 餐厅人均参考价 | 6—24 小时 | 展示来源和更新时间 |
| 酒店搜索报价 | 2—10 分钟 | 仅作为报价快照，预订前重新确认 |
| 门票搜索报价 | 2—10 分钟 | 日期、票种或场次变化时立即重查 |
| 订单前确认结果 | 尽量不缓存 | 直接进入预订链路 |

供应商不可用时应返回明确的降级状态，而不是无期限使用旧报价。

## 六、推荐优先级

### 当前项目的推荐组合

1. **POI 与餐厅参考价：高德地图**
2. **中国境内酒店与门票：优先申请并验证途牛 MCP**
3. **快速 Agent PoC：实测飞猪 flyai 的返回字段和稳定性**
4. **出境游酒店：Booking.com Demand API 或 Expedia Rapid**
5. **出境游景点活动：Viator Partner API**
6. **现有 `trip_service.py` 估算：只作为 fallback**

如果当前目标是先做出可演示版本，最小闭环不是同时解决全部餐厅菜单，而是：

```text
高德发现真实地点
+ 途牛/飞猪查询酒店和门票
+ 高德返回餐厅人均参考价
+ 统一字段标明实时、参考或估算
+ 预订前二次验价
```

## 八、最终判断

这项能力可以实现，而且与 TravelPlanAssistant 当前的 FastMCP、地图服务和行程预算模块很契合。但应将目标表述为“多供应商价格聚合与验价”，而不是寻找一个覆盖所有旅游消费场景的万能接口。

对当前项目最稳妥的下一步，是先实现统一 `PriceOffer` 模型和 provider 接口，再选途牛或飞猪完成酒店、门票 PoC，同时把高德餐厅 `cost` 接成明确标注的“人均参考价”。这样既能尽快得到真实可展示结果，也不会破坏现有估算和预算逻辑。
